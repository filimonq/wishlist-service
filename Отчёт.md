# Отчёт по домашнему заданию № 1

## Доменная область

Wishlist-service — сервис списков желаний к событиям. Пользователь регистрируется, создаёт вишлист, добавляет подарки и делится публичной ссылкой. Друзья могут посмотреть список и забронировать подарок без регистрации, чтобы не подарить одно и то же.

В интерфейсе можно создавать, просматривать, редактировать и удалять вишлисты и подарки. Frontend обращается к backend через HTTP REST API.

## Стек

Backend написан на Go с Gin и pgx, данные хранятся в PostgreSQL. Для авторизации используется JWT, для изменения схемы БД — golang-migrate. Frontend реализован на HTML, CSS и vanilla JavaScript: его файлы лежат в папке `frontend/` и встроены в Go-бинарник. Приложение и PostgreSQL запускаются через Docker Compose.

## Основные сущности

- **Пользователь** — владелец вишлистов. Хранятся его ID, email и хеш пароля.
- **Вишлист** — список желаний с названием, описанием, датой события и публичным токеном. Принадлежит пользователю.
- **Подарок** — элемент вишлиста с названием, описанием, ссылкой и приоритетом. Бронирование хранится в его полях: признак бронирования и время.

## 12 факторов

### 1. Кодовая база

Исходники backend, frontend, миграции и файлы запуска находятся в одном Git-репозитории. Разные развертывания используют одну кодовую базу, а настройки передаются отдельно.

### 2. Зависимости

Зависимости и их версии объявлены в `go.mod`, контрольные суммы хранятся в `go.sum`. Версии mockery, swag, golangci-lint и k6 закреплены в Makefile. Docker изолирует окружение сборки и запуска.

### 3. Конфигурация

Подключение к БД, JWT-секрет, порт сервера и путь миграций задаются через переменные окружения. `DB_CONN` и `JWT_SECRET` обязательны, встроенных секретов нет. Локальные `.env` исключены из Git и Docker-образа; `.env.example` содержит пример настройки.

### 4. Сторонние сервисы

PostgreSQL подключается через `DB_CONN`: сменить экземпляр БД можно без изменения кода. Гексагональная архитектура отделяет бизнес-логику от хранения через интерфейсы репозиториев. Для перехода на MySQL понадобятся новые адаптеры хранения, их подключение и миграции под новую СУБД; бизнес-логика сохранится.

### 5. Сборка, релиз и запуск

Стадии разделены: `make build` собирает образ, `make release` сохраняет конфигурацию, а `make up` запускает готовый образ без пересборки. Команды принимают идентификатор `VERSION` и не перезаписывают уже созданные версии образа и конфигурации.

### 6. Процессы

Backend не хранит постоянное пользовательское состояние в памяти или на своём диске. Данные находятся в PostgreSQL, авторизация работает через JWT без серверных сессий. Экземпляр backend можно заменить другим с той же БД и JWT-секретом.

### 7. Привязка портов

Приложение самостоятельно запускает HTTP-сервер и предоставляет API и frontend через сетевой порт. `HTTP_PORT` задаёт порт сервера, а `HOST_PORT` — порт доступа с хоста в Docker Compose.

### 8. Параллелизм

Backend масштабируется добавлением одинаковых процессов с общей PostgreSQL и JWT-секретом. Команда `make scale VERSION=hw1-v1 REPLICAS=2` запускает два экземпляра; для назначения отдельных портов в конфигурации релиза используется `HOST_PORT=0`. Бронирование выполняется атомарным запросом в БД и не зависит от конкретного экземпляра backend.

### 9. Утилизируемость

HTTP-сервер запускается без выполнения миграций внутри процесса, ожидание подключения к БД ограничено таймаутом. При SIGTERM или SIGINT сервер прекращает приём новых запросов и даёт текущим до пяти секунд на завершение. Сохранённые данные остаются в PostgreSQL после перезапуска backend.

### 10. Паритет разработки и продакшена

Для развертываний используется единый Dockerfile: образ содержит приложение, frontend и зависимости. Локально используется PostgreSQL, а не упрощённая замена другой СУБД. Этот же образ можно запускать в другом окружении, меняя настройки через переменные окружения.

### 11. Логи

Приложение пишет события и HTTP-запросы в stdout, собственных файлов логов не создаёт. В HTTP-логах используется шаблон маршрута вместо URL с публичным токеном. При панике записываются причина и стек вызовов. Docker собирает поток и ограничивает размер логов. Централизованный сбор, хранение и анализ логов пока не настроены.

### 12. Административные задачи

Миграции запускаются отдельным одноразовым процессом через `make migrate VERSION=hw1-v1`. Он использует тот же образ, зависимости и конфигурацию релиза, что и HTTP-сервер. При запуске через Compose backend ждёт успешного завершения миграций.
