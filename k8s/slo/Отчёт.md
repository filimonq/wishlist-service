# SLI, SLO и SLA wishlist-service

## Что измеряется

Wishlist-service позволяет создавать списки желаний и бронировать подарки. Для оценки качества используются метрики API и PostgreSQL из предыдущего задания. Сбор выполняет vmagent, хранение — VictoriaMetrics, графики открываются в vmui.

| SLI | Исходные метрики | SLO |
|---|---|---|
| Доля API-запросов без серверных ошибок | `wishlist_http_requests_total` | Не менее 99,9% без `5xx` |
| Доля быстрых API-запросов | `wishlist_http_request_duration_seconds_bucket` и `_count` | Не менее 99% не дольше 500 мс |
| Доступность подключения к PostgreSQL | `pg_up` и `up` экспортера | Не менее 99,9% хороших минутных отсчётов |

Основной период оценки — последние **7 дней**. Цели выбраны для учебного сервиса. Для оперативных графиков запросные SLI считаются за 5 минут; на демонстрации — за 1 минуту, а доступность по времени — за 10 минут. Короткая запись показывает изменение показателей, но не подтверждает недельный SLA.

## Формулы SLI и SLO

**Серверная успешность API, RBSLO:**

```text
SLI_success(W) = 100 × (N_all(W) − N_5xx(W)) / N_all(W)
SLO: SLI_success(7 дней) ≥ 99,9%
```

Учитываются маршруты `/api/v1/…`, без frontend, Swagger и health checks. Ответы `4xx` считаются обработанными клиентскими ошибками. Индикатор измеряет отсутствие серверных ошибок, а не успех каждого бизнес-действия. При отсутствии запросов результат не определён. Отказы соединения могут не попасть в серверный счётчик, поэтому дополнительно нужен пробер.

**Скорость API, RBSLO:**

```text
SLI_fast(W) = 100 × N_duration_≤0.5s(W) / N_completed(W)
SLO: SLI_fast(7 дней) ≥ 99%
```

Числитель — прирост бакета `le="0.5"`, знаменатель — прирост `_count` той же гистограммы. Учитываются все статусы API. Быстрый ответ `503` удовлетворяет условию скорости, но нарушает условие серверной успешности. Сначала вычисляется прирост каждого счётчика, затем результаты всех реплик суммируются.

**Подключение к PostgreSQL, TBSLO:**

```text
DB_good(m) = 1, если pg_up = 1, up экспортера = 1
             и оба значения получены не более 30 секунд назад;
             иначе 0
SLI_db(W) = 100 × Σ DB_good(m) / N_expected_minutes(W)
SLO: SLI_db(7 дней) ≥ 99,9%
```

Проверка выполняется на минутной сетке. Пропавшие данные считаются плохим отсчётом. За неделю из 10 080 отсчётов допускается не более 10 плохих. Это показатель зависимости: подключение к БД необходимо для работы с вишлистами, но само по себе не гарантирует корректность API.

## SLA приложения

Публичный просмотр контрольного вишлиста должен быть доступен не менее **99,5% времени за 7 дней**. Плановые остановки и демонстрационные сбои входят в расчёт.

Пробер раз в 5 секунд обращается к `/api/v1/public/<token>` через Service приложения. Успех — HTTP `200`, корректный JSON и ожидаемый ID вишлиста за 2 секунды. Хорошая UTC-минута содержит все 12 успешных проверок. Ошибка, пропуск или неполная первая минута делают её плохой.

```text
Availability(W) = 100 × N_good_probe_minutes(W) / N_expected_minutes(W)
SLA выполнено, если Availability(7 дней) ≥ 99,5%
```

За полную неделю допускается не более 50 плохих минут. Пропуски наблюдения не убираются из знаменателя. При нарушении — приоритетное восстановление, разбор причины и меры против повторения. Денежная компенсация для учебного сервиса не предусмотрена.

Пробер находится внутри кластера: проверяет Service, приложение и чтение из БД. Внешние DNS, TLS и доступ из интернета этим сценарием не проверяются. SLA относится к доступности этого сценария; SLO дополнительно задают требования к серверным ошибкам, скорости и БД.

## Что изменено для демонстрации

Добавлена отдельная команда `cmd/prober` в том же Docker-образе. Она экспортирует результаты проверок, длительность, хорошие и плохие минуты на порту `9115`. Адрес и ожидаемый ID задаются через переменные окружения. vmagent обнаруживает Pod по аннотациям. Timestamp-метрики позволяют отличать свежий результат от старого.

Задержки и ошибки вынесены в пакет `internal/adapter/in/http/demo`. Middleware действует только на публичное чтение вишлиста, внутри измерения HTTP-метрик:

- `DEMO_DELAY=1s` — ответы медленнее цели 500 мс, но обычно укладываются в таймаут пробера.
- `DEMO_ERROR_RATE=1` — каждый запрос этого маршрута получает `503`.
- `DEMO_DELAY=0s`, `DEMO_ERROR_RATE=0` — обычная обработка; это значения по умолчанию.

Для проверки индикатора БД предусмотрена краткая остановка PostgreSQL с последующим восстановлением. Переключение режима приложения выполняется через environment variables и rollout. Бизнес-сервисы и репозитории демонстрационных условий не содержат.

[queries.md](queries.md) содержит запросы трёх SLI, линии SLO и расчёт доступности рядом с порогом SLA. [README.md](README.md) содержит команды запуска и порядок демонстрации.

После отключения сбоя оперативные SLI восстанавливаются по мере обновления минутного окна. Доступность за 10 минут ещё некоторое время учитывает произошедшие плохие минуты — устранение сбоя не стирает историю.
