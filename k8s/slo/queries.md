# Запросы для vmui

Откройте `http://localhost:8428/vmui/`. Каждый блок — отдельный запрос. Для сравнения с целью добавьте второй запрос с константой в тот же график. Единицы всех четырёх основных графиков — проценты.

Запросы используют MetricsQL и короткие окна для демонстрации. Проверка на данных minikube выполняется при общем запуске.

## 1. API без серверных ошибок

Доля запросов без `5xx` за последнюю минуту:

```promql
WITH (
  total = sum(increase(wishlist_http_requests_total{
    namespace="wishlist", app="wishlist-service", route=~"/api/v1/.*"
  }[1m])),
  errors = sum(increase(wishlist_http_requests_total{
    namespace="wishlist", app="wishlist-service", route=~"/api/v1/.*", status=~"5.."
  }[1m])) or vector(0)
)
100 * (1 - errors / total) and (total > 0)
```

Линия цели SLO:

```promql
vector(99.9)
```

Отсутствие ряда ошибок означает ноль ошибок, но отсутствие трафика не превращается в 100% успеха. В режиме `DEMO_ERROR_RATE=1` показатель снижается. Если до API совсем не доходят запросы, график может прерваться — доступность в таком случае оценивает пробер.

## 2. API не дольше 500 мс

```promql
WITH (
  fast = sum(increase(wishlist_http_request_duration_seconds_bucket{
    namespace="wishlist", app="wishlist-service", route=~"/api/v1/.*", le="0.5"
  }[1m])),
  total = sum(increase(wishlist_http_request_duration_seconds_count{
    namespace="wishlist", app="wishlist-service", route=~"/api/v1/.*"
  }[1m]))
)
100 * fast / total and (total > 0)
```

Линия цели SLO:

```promql
vector(99)
```

В режиме `DEMO_DELAY=1s` показатель снижается. Успешный ответ за секунду удовлетворяет проверке доступности пробера, но нарушает требование скорости.

## 3. Подключение к PostgreSQL

Доля хороших минутных отсчётов за последние 10 минут:

```promql
WITH (
  good = (
    max(
      (last_over_time(pg_up{namespace="wishlist", app="wishlist-postgres"}[30s]) == 1)
      and
      (last_over_time(up{namespace="wishlist", app="wishlist-postgres"}[30s]) == 1)
    ) or vector(0)
  )
)
100 * sum_over_time(good[10m:1m]) / 10
```

Линия цели SLO:

```promql
vector(99.9)
```

`last_over_time(...[30s])` ограничивает свежесть исходных данных. При недоступности БД или отсутствии свежих метрик отсчёт равен нулю. Знаменатель фиксирован: 10 ожидаемых минут, а не только минуты с имеющимися данными.

## 4. Доступность сценария и SLA

```promql
clamp_max(
  100 * (
    sum(increase(wishlist_probe_minutes_total{
      namespace="wishlist", app="wishlist-prober", result="good"
    }[10m])) or vector(0)
  ) / 10,
  100
)
```

Линия обязательства SLA:

```promql
vector(99.5)
```

Счётчик увеличивается только после полностью хорошей минуты. В знаменателе — 10 ожидаемых минут. Когда пробер не работает, новые хорошие минуты не появляются: отсутствие наблюдений не улучшает доступность. `increase()` учитывает сбросы счётчиков и данные разных Pods. Момент появления изменения на графике зависит от очередного сбора метрик.

`clamp_max` ограничивает результат 100% на границе окна из-за дискретного сбора минутных событий. Для точного календарного учёта потребовалась бы отдельная история минутных результатов; здесь используется оценка по собранным счётчикам.

В первые 10 минут после запуска окно ещё не заполнено. Для исходного графика со стабильной доступностью дайте проберу поработать не менее 11 минут без ошибок. Плохие минуты после сбоя будут видны, пока не выйдут из 10-минутного окна.

## Текущий результат пробера

Для проверки восстановления без ожидания всего 10-минутного окна:

```promql
last_over_time(wishlist_probe_success{
  namespace="wishlist", app="wishlist-prober"
}[30s])
```

`1` — последняя проверка успешна, `0` — неуспешна. Отсутствие свежих данных здесь означает отсутствие наблюдения, а не успех. Этот график дополняет расчёт SLA, но не заменяет его.

## Основные периоды

Для обычных оперативных графиков в первых двух запросах замените `[1m]` на `[5m]`. Для недельных запросных SLI — на `[7d]`.

Для недельной доступности БД замените `[10m:1m]` на `[7d:1m]` и знаменатель `10` на `10080`. Для SLA замените `[10m]` на `[7d]` и знаменатель `10` на `10080`. Полная недельная оценка требует 7 дней наблюдений.

SLO и SLA — заданные цели, поэтому их линии постоянные. Меняются фактические SLI и доступность относительно этих линий.

Справочник синтаксиса: [MetricsQL](https://docs.victoriametrics.com/victoriametrics/metricsql/).
